# 错误处理策略

> 定这条策略的原因：仓里有 74 处 `_ =`（显式忽略返回值），一锅端地改会把
> 「尽力而为」的地方变成噪音，也会把真正的 bug 埋在日志里。所以先分级，再用
> 测试把它钉住。

## 三档

### 一档：必须上报（error 往上返回，或写进用户可见状态）

- 涉及**数据一致性**：读写会话、课程、state、stats 的失败
- 涉及**用户可见状态**：该成功而没成功、该保存而没保存
- 涉及**外部副作用**：调用外部接口、写用户文件

判据一句话：**如果失败了而用户以为成功了，就是一档。**

### 二档：允许尽力而为（可以 `_ =`，但必须写理由）

- 备份写盘（`.bak`）、临时文件清理
- 日志、指标上报
- 编码失败后的退化（例如时间格式化失败退回空串）
- 关闭资源的 `defer resp.Body.Close()`

写法要求：

```go
_ = os.WriteFile(final+".bak", b, 0o644) // 允许忽略：备份失败不影响主文件，主文件已是原子写
```

**没有注释的 `_ =` 一律视为三档违规。**（历史代码被预算豁免，新代码不豁免。）

### 三档：禁止忽略（必须现场处理）

- 密钥、凭据、权限
- 加密、签名
- 用户数据删除

这三类一旦失败，宁可让操作整体失败，也不能「默默继续」。

## 怎么守住

`internal/arch/errors_test.go` 把当前 74 处钉成预算：

- 新代码想忽略，要么写注释并按二档处理，要么把预算改大——改预算必须在提交说明里写理由
- 预算只许减不许增（修一处就把数字改小）

这不是洁癖：预算是一份「技术债台账」，涨了你就得说清为什么。
