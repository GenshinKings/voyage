# 我们的 Harness（小队版）

借 HelixHarness 的骨架，改到我们的现实：**ZCode 实现、小穗审、主人拍板**，没有 Codex/Claude Code 那样的 host hook，所以「闸门」不靠插件，靠可执行的命令和验收证据。

## 四类文档，各管一件事

| 目录 | 回答什么 | 谁维护 |
| --- | --- | --- |
| `docs/knowledge/` | 这系统怎么运作、哪些业务规则和边界不能碰 | 人在需要时补 |
| `docs/specs/` | 这次要做什么、**什么算做完**（带证据） | 提任务时写 |
| `docs/checks/` | 每次必须跑哪些命令、跑不过就不许提交 | 一次写好，长期用 |
| `docs/harness/` | 流程本身（本文件、模板、清单） | 改流程时改这里 |

不设 `hooks/`：ZCode 没有 host 级钩子，用命令代替，命令写在 `docs/checks/`，谁跑都一样。

## 三步，顺序不能改

1. **PROPOSE** —— 只写范围与验收，不写代码。
   - 上限：给 ZCode 的提案要求 **≤ 15 行**（它默认会写 40 分钟的长文，必须压）
   - 必须包含：做什么 / 不做什么 / 验收命令 / 失败时怎么判
2. **APPLY** —— 按提案写代码，每完成一小步就跑 `docs/checks/` 里的命令。
   - 提交信息写「做了什么 + 验证了什么」，不写「优化」「改进」
3. **ARCHIVE** —— 回看这一轮：把验证过的规则沉淀成 `docs/knowledge/` 里的一条，把新发现的坑写进 `docs/knowledge/pitfalls.md`。

## 硬闸门（跑不过就别提交）

```bash
go test -count=1 ./...
gofmt -l ./cmd ./internal ./fsrs     # 输出必须为空
go vet ./...
```

三条全绿才算 APPLY 完成；有红就不许进 ARCHIVE。

## 为什么这么定

- 我们踩过的坑几乎都不是「模型不聪明」，是**没有验收标准**，于是双方都在凭感觉说「做完了」
- 长文=不可验证。压到 15 行不是为了省字，是为了逼出可判定的结论
- Archive 一步最容易被跳过，也最值钱：它能防止同一个坑踩第二次
