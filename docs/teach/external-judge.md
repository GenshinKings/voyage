# 第三方判定（人工/外部裁判）

> 解决的问题：有些关卡和答案，**机器判不了**——「骨架跑起来了没有」「这个方案是不是他想的」
> 「README 别人能不能照着用」。硬用模型判会得出「看起来像对的」结论，等于放水。
> 所以引入第三方判定：它可以是一个人，也可以是另一个更贵的模型。

## 一、三种角色

| 角色 | 谁 | 能做什么 |
|---|---|---|
| 学习者 | 用户本人 | 交产物、看判词、申诉一次 |
| 助教 | 本机模型 | 教学、自动判定（能判的那类） |
| 裁判 | 另一个人 / 另一个模型 | 只判助教判不了的那类，判词带依据 |

**关键约束：裁判不改教学内容，只回答「过 / 不过 / 差在哪」。**
一旦让裁判也去讲解，它就会开始替学习者思考，等于换了个人上课。

## 二、什么情况交给裁判

按优先级：

1. 关卡 `Expect` 为空（骨架、最小闭环、README、三天后还用吗）
2. 模型判定置信度低（一次判不过、重试后仍判不过，且学习者申诉）
3. 涉及「这是不是他自己做的」（AI 代写嫌疑）

**不交给裁判的**：有 `Expect` 能自动对上的关卡、错因分类（那是助教的核心能力）。

## 三、状态机

```
待判(ai_uncertain) → 送裁判 → 过 / 不过
                              ↓
                          不过 → 判词写进会话（含 where + action）→ 学习者继续
                              ↓
                          学习者申诉一次 → 二次裁判（必须换人/换模型）
```

规则：

- **每关最多申诉一次**，防止无限拉锯
- 裁判判词必须带 `where`（差在哪）和一条 `action`（下一步），不允许只写结论
- 裁判判定与助教判定冲突时，**以裁判为准**，并把这次冲突记进 metrics（它是「助教判不准」的证据）

## 四、怎么实现（两步走）

### 第一步：不改变现有链路（现在做）

- `run.Stage` 已支持「外部判定」入口：`SubmitJudged(output, pass, reason)`
- 服务端已有 `judgeStage`（模型裁判）；把它当成「默认裁判」
- 需要人工时，产物写入 `outpost2-data/reviews.json`，状态 `pending`

接口（只读 + 两条写）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/reviews` | 待判列表（谁能看到由部署形态决定） |
| POST | `/api/reviews/{id}/verdict` | `{pass, where, action}` |

### 第二步：接外部（等你确认产品形态再动）

- 单人本地版：裁判入口就是**用户自己**（「我判它过了」），用于没模型时的兜底
- 多人版：加一个「判卷人」角色 + 邀请码，判卷人只看产物和验收标准

## 五、为什么第二步要等

「谁来当裁判」是产品定位问题，不是技术问题：

- 单人版：裁判=自己，等于自评，只解决「没模型也能往下走」
- 导师版：裁判=真人，能卖钱，但要处理激励（谁付钱、判得快不快）
- 社区版：裁判=其他学习者，需要防刷分和串通

这三种的代码差别不大，但**规则差别很大**。等你定了形态，我再实现。
