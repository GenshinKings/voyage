# 3.0 转向：从「学会」到「交付」

> 2026-10-31 · 决策记录 · 对应 git tag `v3.0.0`

## 当时的判断

1. **写代码这件事在贬值。** 主人原话：「未来需要的肯定不是敲代码的」。
   这句话对了一半：语法和 API 不值钱了，但「判断它对不对、能不能兜住」更值钱了。
2. **问答式教学不产生交付。** 1.0/2.0 的教学形态是「我讲 → 你听 → 出题检查」。
   结果是：概念可能记得住，但人还是没交付过任何东西。
3. **目标用户不是零基础学生，是「跟过教程、自己琢磨过、从没交付过」的人。**
   这类人不缺知识入口，缺的是「从模糊需求走到能用」的整段经验。

## 决定做什么

四步闭环：

```
出真实问题 → 你做（可用 AI） → 记录动作/卡点/提示词 → 从卡点出下一题
```

与之配套的三条硬规则：

- **每关必须有可验证收**：跑得起来 / 有测试 / 别人照着能用。没有验收的关卡不许发布
- **允许全程用 AI，但必须留痕**：你判断了什么、为什么这么定
- **出题按错误类型，不按章节顺序**：概念错 → 概念题；粗心 → 只提醒流程

## 放弃的做法

| 放弃 | 为什么 |
|---|---|
| 知识图谱式教学（把概念连成网） | 图很好看，但把「学会」当成目标；用户要的是交付物 |
| 按章节推进的题库 | 与你的实际卡点无关；越刷越像考试，不像做项目 |
| 「AI 代做」 | 会得到一堆交付物和一个不会的人 |
| 追求「学完 Go」 | 只在需要时补最小集：读得懂、改得动、出错能定位 |

## 留下的代价（老实说）

1. **难度不可预期**：真实问题有时十分钟能过，有时三天。体验会比「一天一课」差。
2. **验收很难标准化**：能跑的检查好写，「别人照着能用」只能靠人判。
3. **零基础用户需要更多脚手架**：第一关要拆成「装环境 → 跑到输出 → 再谈代码」，
   否则第一步就劝退。这是 3.0 必须额外补的成本。
4. **旧内容会显得多余**：已经写好的知识点课程要重新定位成「查手册」，不再是主线。
